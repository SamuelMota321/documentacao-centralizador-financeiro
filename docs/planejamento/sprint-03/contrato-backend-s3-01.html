Decision register

Decision Recorded direction Authority / evidence
D1 — OFX variants and encodings Accept OFX 1.x SGML and OFX 2.x XML using US-ASCII and UTF-8. This is a compatibility recommendation under the user's delegation; it is not a claim about which format is most common in Brazilian bank exports. User delegated selection to the most common option. Official OFX sources document both families; no reliable Brazilian distribution evidence was found. See https://financialdataexchange.org/about-fdx/ofx-work-group/ and https://www.financialdataexchange.org/common/Uploaded%20files/OFX%20files/OFX%202.2.pdf.
D2 — upload cap and storage Initial cap: 10 MiB per file. Authenticated backend streams the object to private R2; PostgreSQL retains metadata/reference only. User delegated to best practice; Architecture RN-013 and Cloud Run architecture. The cap is a conservative starting limit, not a measured user-file distribution. Cloud Run request ceiling reference: https://docs.cloud.google.com/run/quotas.
D3 — OFX destination User explicitly selects an existing active local account at confirmation. User decision D3; account ownership/active-account patterns in current Accounts and Transactions modules.
D4 — OFX identity/fallback FITID/ID per destination account. If missing, date/amount/description fallback warns in preview but does not require row-by-row approval. User decisions D4 and D4-1; RN-006. Risk: false-positive fallback matches can cause a new row to be skipped.
D5 — re-import Ignore duplicates and import new records from the same file/run. User decision D5; HU-004/RN-006.

Approved API contract direction

These operations are the approved S3-01 contract direction. They describe the client/backend interface; this phase does not implement runtime handlers. All protected operations require the existing Auth0 Bearer scheme. Tenant identity is derived from the authenticated context.

OFX

Method and path Request Success behavior
POST /api/v1/ingestions/ofx/previews multipart/form-data with one file field named file; maximum 10 MiB 201 with a ready preview, or 202 when preview processing is queued. Returns an ImportRun representation.
POST /api/v1/ingestions/{importRunId}/confirmations JSON with destinationAccountId; requires Idempotency-Key 200 when completed inline or 202 when queued. Runs using this endpoint persist only new rows and report ignored duplicates.
GET /api/v1/ingestions/{importRunId} No body 200 with current status and available preview/result.

Preview rows expose the normalized date, amount, description, primary external identity when present, duplicate disposition and warnings. The fallback warning is advisory; confirmation remains available. Run results expose imported, ignored and failed counts plus sanitized item errors.

Pluggy initial connection/import

Method and path Request Success behavior
POST /api/v1/connections/pluggy/sessions Authenticated request; no provider secret from client 201 with a connection session, limited client connect token and expiration.
POST /api/v1/connections/pluggy/completions JSON references the connection session and provider Item; requires Idempotency-Key 202 after the backend verifies the provider reference, stores consent metadata and starts the initial ImportRun.
GET /api/v1/connections/{connectionId} No body 200 with connection/consent state, per-type availability and initial-import state.
PUT /api/v1/connections/{connectionId}/accounts/{providerAccountId}/mapping JSON with the user's selected accountId 200 with the recorded association. The run waits until every required association is resolved, then continues.
POST /api/v1/connections/{connectionId}/disconnect No body 200 with disconnected state. Stops future collection and leaves local data intact.

Provider credentials remain server-side. The client token is limited to completing provider authorization. Consent scopes and timestamps are obtained/verified by the backend against the provider; a client cannot assert a tenant, scope or consent state.

Shared response and retry behavior

  • Responses use application/json. File intake uses multipart/form-data.
  • Errors use the repository's application/problem+json shape with type, title, status, code and detail.
  • Proposed success codes are 201 for newly created preview/session, 202 for accepted asynchronous work, and 200 for reads and completed state changes. Relevant error classes are 400 invalid input, 401 unauthenticated, 403 unauthorized, 404 missing/other-tenant resource, 409 invalid state or idempotency conflict, 413 oversized file, 415 unsupported media type, 422 structurally invalid OFX, and 503 provider unavailable.
  • Mutating POST operations that create a run/session or start work require Idempotency-Key. Follow the current transaction pattern: 1–255 characters, scoped by tenant and operation; the same key and normalized payload replays the prior resource/result, while a different payload conflicts. PUT mapping is naturally idempotent.
  • ImportRun status values: preview_ready, awaiting_account_mapping, queued, processing, completed, completed_with_errors, failed and expired.
  • Connection status values: pending_authorization, connected, partially_available, expired, revoked and disconnected. Consent values: granted, expired and revoked.
  • ImportRun metadata/results are tenant-owned and retained for 90 days. Raw source objects are deleted when the run reaches a terminal state.
  • A disconnect changes connection state and stops new provider reads; it does not erase accounts or transactions already persisted in PostgreSQL.

The existing OpenAPI remains the generated contract for implemented NestJS routes. This S3-01 document records the approved future operations without publishing unimplemented runtime routes into the generated OpenAPI. S3-02/S3-05 must implement matching handlers and update OpenAPI from the established NestJS route/schema source.

Backend ownership and controls

Concern Owner and rule
Connection, provider Item reference, consent and linked accounts Accounts owns persistence. New local accounts are created through its public Application interface; existing accounts are associated only by user selection.
Upload object, ImportRun, preview, status and orchestration Ingestion owns file reference/run lifecycle. It calls Accounts and Transactions through public Application interfaces.
Normalized transaction and duplicate identity Transactions owns transaction invariants and persistence. It receives normalized commands and tenant context; Ingestion does not write its tables.
Authentication/authorization Auth0 validates JWT; NestJS Guard and application policy authorize; tenant comes only from internal identity resolution.
Idempotency/concurrency Key claims and external identity constraints must be tenant-scoped. Prevent overlapping initial imports for the same connection. Provider IDs are unique within provider connection/account scope.
RLS and transactions New tenant-owned tables carry tenant ownership and FORCE RLS under the RLS ADR. Set tenant context transaction-locally. Do not call Pluggy, R2 or QStash from inside that transaction.
Audit/logging D15 events use audit records without source files or financial row payloads. Failed/partial result is stored in the ImportRun; technical logs are sanitized and distinct from business audit.
Source of truth PostgreSQL contains authoritative connection/run/account/transaction state. R2 stores only source objects for the approved lifetime. External outage cannot delete persisted valid data.
