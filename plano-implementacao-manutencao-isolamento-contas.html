PlanoPré-condições e baseline

1. Finalidade e limite de autorização

Status: aprovado em 11/09/2026. Este plano traduz a Especificação de Manutenção e Isolamento de Contas 1.0 em fases backend ordenadas. Ele não implementa o backend, não autoriza operação destrutiva, não autoriza SQL em banco compartilhado e não autoriza deploy.

2. Pré-condições verificadas

  • Backend NestJS 11, TypeScript, Prisma 7, PostgreSQL, Zod, Vitest e Supertest estão declarados em package.json.
  • O prefixo /api/v1, Swagger/OpenAPI, Auth0 Guard, Identity resolver, módulos Accounts/Identity e Problem Details para S1-04/S1-05 existem.
  • O modelo Account possui origem manual/connected, moeda BRL, saldo decimal, archivedAt, índices de tenant e migration de fundação/RLS.
  • PrismaTenantTransaction valida contexto e define app.current_tenant_id localmente antes do callback; RLS atual está aplicado às quatro tabelas de Identity/Accounts.
  • O backend atual ainda não possui use cases de update/deactivate, tabela/modelo de auditoria, request id, migration de audit ou rotas PATCH/deactivate.
  • O repositório backend está limpo na branch main, com os commits de fundação e autenticação/contas anteriores. Testes de integração dependem de PostgreSQL local.

3. Dependências de execução

A ordem mínima é F0 baseline → F1 domínio/Application e unidade de trabalho → F2 schema/migration/audit/RLS → F3 adapters e REST/OpenAPI → F4 testes e verificação. F3 não deve ser integrado antes de F2 e F4 não deve declarar sucesso sem banco migrado e role cfi_test sem BYPASSRLS.

Fase 1Domain e Application

          

            
6. Modelo de aplicação

            
    
              
  1. Adicionar ao Domain uma operação de update que receba campos já tipados/normalizados, preserve tenantId, origem, currency, providers, external id e timestamps, e recuse conta arquivada.
    2. 
              
  2. Manter Money, BalanceReferenceDate, normalização e tipos de conta como invariantes independentes de Zod.
    3. 
              
  3. Criar UpdateAccount e DeactivateAccount; ambos recebem TenantContext e request id explícitos e não importam HTTP, NestJS, Prisma ou logger.
    4. 
              
  4. Calcular no Application a representação final, verificar origem, executar duplicidade somente quando campos de identidade mudarem e construir metadata segura.
    5. 
              
  5. Usar uma unidade de trabalho tenant-aware para entregar Account repository e Audit writer sobre o mesmo transaction client.
    6. 
            

            
7. Justificativa da unidade de trabalho

            
O port existente encapsula uma transação para Accounts, mas não expõe uma forma de escrever em Audit atomicamente sem acoplar Application a Prisma ou abrir uma segunda transação. A menor extensão compatível é um port de unidade tenant-aware que compõe ports de Accounts e Audit dentro do callback transacional. Isso resolve a invariável “mutação aceita implica auditoria aceita”, preserva Hexagonal/Clean e não introduz outbox, evento, fila ou mecanismo de consistência eventual.

            
8. Contrato do Audit writer

            
O writer recebe somente um comando validado contendo tenant, actor, action, resource type/id, outcome, request id e metadata permitida. O adapter realiza INSERT parametrizado sem retornar ou consultar registros para o runtime. Erros de constraint, privilege ou conexão sobem tipados até o boundary transacional; o mapper HTTP devolve somente INTERNAL_ERROR.

            
9. Request id

            
Criar middleware inbound que valide UUID canônico no header X-Request-Id, gere UUIDv4 quando ausente ou inválido, anexe o valor à request e ao response e forneça o valor aos casos de uso. A entrada nunca participa da autorização nem é escrita sem validação. O mecanismo não altera o formato Problem Details.

          

          

        


        

          
Fase 2Prisma, schema e migration

          

            
10. Schema Prisma e migration forward-only

            
Atualizar prisma/schema.prisma com os três enums e o model AuditRecord descritos na especificação. A migration será criada com prisma migrate dev --create-only, revisada manualmente e receberá SQL customizado para owner, grants, checks, RLS e policies. Nenhuma migration já aplicada será editada.

            
11. SQL obrigatório da migration

            
    
              
  • Criar enums audit_action, audit_resource_type e audit_outcome, tabela public.audit_records, PK, FKs RESTRICT, default UUID, timestamptz(3), JSONB default e checks de metadata.
    • 
              
  • Criar índices audit_records_tenant_created_at_id_idx, audit_records_tenant_resource_created_at_idx e audit_records_request_id_idx.
    • 
              
  • Definir owner cfi_owner, revogar privilégios de PUBLIC, conceder INSERT ao runtime e SELECT/INSERT somente ao test.
    • 
              
  • Habilitar e forçar RLS; criar policy de INSERT runtime/test e SELECT test; não criar UPDATE/DELETE policy nem grants.
    • 
              
  • Incluir audit_records nas consultas de readiness que impedem runtime owner/superuser/BYPASSRLS.
    • 
            

            
12. Adapter Prisma

            
Estender o adapter de Accounts com consultas por id e tenantId, lock de linha dentro do callback transacional, exclusão de arquivadas para PATCH e retorno uniforme de ausência. Update deve enviar somente campos permitidos; deactivate deve executar update condicional de archivedAt. O Audit adapter usa o mesmo tx e não realiza I/O externo.

            
O mapeamento Prisma/Domain preserva Decimal como string canônica e datas UTC. SQLSTATE de ausência não deve ser usado para distinguir cross-tenant; violação inesperada de RLS, FK ou check recebe erro interno tipado.

          

          

        


        

          
Fase 3RLS e verificação SQL

          

            
13. Policies e roles

            
Reutilizar app_private.current_tenant_id() e o padrão do ADR. O contexto é sempre definido com set_config(..., true) dentro da interactive transaction. Role runtime permanece NOSUPERUSER, NOBYPASSRLS, sem ownership e sem herança administrativa. A função de provisionamento continua sendo o único caminho privilegiado de bootstrap de Identity.

            
14. Verificação independente

            
Atualizar scripts/database/verify-rls.sql para verificar cinco tabelas com RLS/force, políticas esperadas, owner, grants e atributos dos papéis. Acrescentar blocos transacionais que, como cfi_test, confirmem:

            
    
              
  • tenant A lê seus accounts/audits e tenant B não lê as linhas de A;
    • 
              
  • INSERT com tenant alheio falha; INSERT sem contexto ou contexto inválido falha;
    • 
              
  • UPDATE/DELETE em audit_records são negados por privilégio/policy;
    • 
              
  • UPDATE de accounts não consegue trocar tenant_id;
    • 
              
  • pool reuse não herda contexto de uma transação anterior.
    • 
            

            
15. Atomicidade e recuperação

            
A alteração de Account e INSERT de Audit são uma unidade curta. Se a migration falhar em ambiente ainda não migrado, corrigir a migration antes de aplicar; se já aplicada, criar nova forward migration. Se uma aplicação parcialmente migrada detectar ausência de audit, readiness/health deve impedir tráfego de manutenção até o estado esperado. Não usar rollback destrutivo nem db push.

24. Riscos e correção

            
    
              
  • Auditoria falha: rollback transacional; investigar privilégio/schema antes de retry.
    • 
              
  • Migration parcialmente aplicada: não editar histórico; fazer forward-correction ou restore controlado.
    • 
              
  • Privilégio runtime inseguro: readiness falha; corrigir role/grant, não elevar aplicação.
    • 
              
  • Lock aumenta espera: medir somente após comportamento correto; não remover ownership para performance.
    • 
              
  • Contrato OpenAPI divergente: parar integração dos clientes e corrigir contrato/geração antes de merge.

26. Critério de conclusão

            
A implementação futura somente poderá ser considerada concluída quando o contrato normativo estiver refletido no código, migration e OpenAPI, todos os testes e comandos relevantes executarem com resultado registrado, RLS for comprovado por role sem bypass, e o diff backend permanecer limitado ao plano aprovado. Qualquer mudança material de escopo, rota, schema, role, dependência, persistência ou operação compartilhada exige nova aprovação.

            
27. Declaração de não autorização

            
Este documento é um plano. Ele não autoriza implementação backend, criação/aplicação de migration, execução de SQL destrutivo, escrita em banco compartilhado, alteração de roles/grants em ambiente remoto, deploy, ou modificação de clientes. Esses atos exigem autorização operacional própria e evidência de ambiente seguro.
