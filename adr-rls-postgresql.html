ADR-001 · Segurança e tenancy

Isolamento por tenant com PostgreSQL RLS

Decisão fail closed e segura para Prisma, Neon pooling e NestJS.

Versão 1.009 set 2026Status: aceito

Neste documento

ADR integral

ADR RLSContexto

1. Status, contexto e escopo

Status: aceito em 09/09/2026. Esta decisão fecha o mecanismo pendente na Arquitetura 1.5 para S1-02/S1-03. Aplica-se às tabelas tenants, users, identity_links e accounts, ao tráfego REST e a trabalhos autenticados que as acessem.

Drivers: RN-001 a RN-004, RNF-002, menor privilégio, reutilização segura de conexões serverless, independência de Domain/Application e testes cross-tenant reproduzíveis. RLS é defesa em profundidade e não substitui autenticação Auth0, autorização NestJS, TenantContext, filtros de repositório ou constraints.

2. Threat model e objetivos

  • Erro de filtro, ID controlado pelo cliente, consulta raw incorreta ou reuso de conexão não pode revelar linha de outro tenant.
  • INSERT/UPDATE não pode atribuir ownership alheio; UPDATE não pode mover linha entre tenants; DELETE cross-tenant não pode afetar linhas.
  • Contexto ausente, vazio, malformado ou expirado nega acesso.
  • São considerados: requisições concorrentes, pooling transacional, retries, jobs, migrações e provisionamento inicial.
  • Não cobre comprometimento do papel de migration/provisionamento, superusuário, exfiltração de credenciais nem vulnerabilidade do próprio PostgreSQL.

ADR RLSFluxo decidido

4. Decisão de contexto

  1. Guard NestJS valida assinatura, algoritmo, issuer, audience, expiração e permissões do access token Auth0.
  2. Identity recebe somente provider='auth0', issuer e subject já validados e resolve userId/tenantId internos.
  3. Application recebe TenantContext { userId, tenantId } explícito, sem Request, JWT ou tipos NestJS.
  4. O adapter abre uma interactive transaction curta e executa set_config('app.current_tenant_id', tenantId, true) como primeira instrução.
  5. Toda operação protegida usa exclusivamente o cliente transacional tx. Commit/rollback elimina o valor local.

O adapter valida UUID canônico antes de abrir a transação. Contexto ausente ou inválido gera InvalidTenantContext. A função SQL também converte valor inválido em NULL: SELECT retorna zero linhas e WITH CHECK rejeita mutações.

5. Prisma, pooling e transações

  • Runtime usa endpoint pooled -pooler do Neon; migration e administração usam endpoint direto.
  • Não são usados SET de sessão, RESET, temporary tables nem session advisory locks.
  • Interactive transaction permanece curta e não contém chamada Auth0, Pluggy, HTTP ou outra I/O externa.
  • Transação tenant-aware não é aninhada. Casos compostos recebem o mesmo tx; código interno não inicia outra $transaction.
  • Retry repete a unidade completa, inclusive set_config, somente para falhas transitórias classificadas e operações idempotentes.
  • Jobs resolvem TenantContext a partir de IDs internos mínimos e seguem o mesmo wrapper.
type TenantContext = Readonly<{ tenantId: string; userId: string }>;

return prisma.$transaction(async (tx) => {
  await tx.$queryRaw`
    SELECT set_config('app.current_tenant_id', ${context.tenantId}, true)
  `;
  return operation(tx);
});
ADR RLSPapéis e ownership

6. Papéis e privilégios

PapelAtributosUso
cfi_ownerNOLOGIN, NOBYPASSRLSProprietário dos objetos; sujeito a FORCE RLS.
cfi_migratorLOGIN administrativoSomente migration direta; nunca tráfego da aplicação.
cfi_runtimeLOGIN, NOSUPERUSER, NOCREATEDB, NOCREATEROLE, NOBYPASSRLSTráfego API/jobs com DML mínimo.
cfi_identity_provisionerNOLOGIN, BYPASSRLSDono exclusivo da função estreita de resolução/provisionamento.
cfi_testLOGIN, NOBYPASSRLSSomente banco/branch isolado; DML necessário à matriz.

Papéis de login runtime/test devem ser criados por SQL e auditados em pg_roles. Papéis criados pelo Console/CLI/API do Neon podem herdar neon_superuser e não servem para tráfego protegido. Startup falha se runtime for superuser, possuir BYPASSRLS ou for owner das tabelas.

Revogar de PUBLIC: CREATE no schema público quando aplicável, todos os privilégios nas quatro tabelas e EXECUTE nas funções novas. Runtime recebe USAGE nos schemas, SELECT nas quatro tabelas, INSERT/UPDATE/DELETE em accounts e EXECUTE somente nas funções aprovadas. Alteração de identity_links ocorre apenas por funções estreitas com comprovação de identidade. Runtime não recebe TRUNCATE, REFERENCES, TRIGGER, ownership ou grant option.

7. Caminhos de propriedade

  • tenants.id = current_tenant_id().
  • users.tenant_id = current_tenant_id().
  • identity_links.user_id → users.tenant_id = current_tenant_id().
  • accounts.tenant_id = current_tenant_id().

ENABLE e FORCE ROW LEVEL SECURITY são obrigatórios nas quatro tabelas. Policies são permissivas, específicas por comando e limitadas a runtime/test.

CREATE OR REPLACE FUNCTION app_private.current_tenant_id()
RETURNS uuid LANGUAGE sql STABLE PARALLEL SAFE
SET search_path = pg_catalog
AS $$
  SELECT CASE
    WHEN value ~* '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$'
      THEN value::uuid
    ELSE NULL
  END
  FROM (VALUES (current_setting('app.current_tenant_id', true))) AS setting(value)
$$;

Policies não substituem GRANT. Runtime não recebe INSERT/UPDATE/DELETE direto em tenants/users nem UPDATE em identity_links, embora as policies existam para cobertura completa e teste isolado. Antes de recriar policy, migration usa DROP POLICY IF EXISTS somente quando a mudança foi explicitamente planejada.

ADR RLSBootstrap

10. Resolução e provisionamento de identidade

Antes de existir TenantContext, a aplicação chama app_private.resolve_or_provision_identity('auth0', issuer, subject). A função é SECURITY DEFINER, pertence a cfi_identity_provisioner NOLOGIN BYPASSRLS, fixa search_path=pg_catalog, qualifica todos os objetos e tem EXECUTE revogado de PUBLIC.

  1. Rejeita provider diferente de auth0, issuer sem HTTPS, valores vazios, controles e excesso de 255 caracteres. A allowlist do issuer é validada pelo backend antes da chamada.
  2. Busca exatamente `(issuer, subject)` e retorna somente user_id/tenant_id se já existir.
  3. Se não existir, gera tenant e user UUID, insere tenant, user e primeiro link na mesma transação.
  4. Unique violation concorrente desfaz o subbloco, relê o vínculo vencedor e retorna o mesmo par.
  5. Qualquer outra falha aborta integralmente; não permanece tenant órfão.

O issuer aceito não é fornecido livremente pelo cliente: deve coincidir com configuração do backend e com o JWT validado. A função não lista usuários, não recebe tenant/user arbitrário, não vincula segunda identidade e não acessa accounts. Vinculação adicional será caso de uso separado com prova das duas identidades.

CREATE OR REPLACE FUNCTION app_private.resolve_or_provision_identity(
  p_provider text,
  p_issuer text,
  p_subject text
) RETURNS TABLE(user_id uuid, tenant_id uuid)
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog
AS $$
DECLARE
  v_user_id uuid;
  v_tenant_id uuid;
BEGIN
  IF p_provider IS DISTINCT FROM 'auth0'
     OR p_issuer IS NULL OR p_issuer !~ '^https://'
     OR char_length(p_issuer) NOT BETWEEN 1 AND 255
     OR p_issuer IS DISTINCT FROM btrim(p_issuer)
     OR p_issuer ~ '[[:cntrl:]]'
     OR p_subject IS NULL
     OR char_length(p_subject) NOT BETWEEN 1 AND 255
     OR p_subject IS DISTINCT FROM btrim(p_subject)
     OR p_subject ~ '[[:cntrl:]]' THEN
    RAISE EXCEPTION 'invalid identity'
      USING ERRCODE = '22023';
  END IF;

  LOOP
    SELECT il.user_id, u.tenant_id
      INTO v_user_id, v_tenant_id
      FROM public.identity_links AS il
      JOIN public.users AS u ON u.id = il.user_id
     WHERE il.issuer = p_issuer
       AND il.subject = p_subject;

    IF FOUND THEN
      RETURN QUERY SELECT v_user_id, v_tenant_id;
      RETURN;
    END IF;

    v_tenant_id := gen_random_uuid();
    v_user_id := gen_random_uuid();

    BEGIN
      INSERT INTO public.tenants (id) VALUES (v_tenant_id);
      INSERT INTO public.users (id, tenant_id) VALUES (v_user_id, v_tenant_id);
      INSERT INTO public.identity_links (id, user_id, provider, issuer, subject)
      VALUES (
        gen_random_uuid(), v_user_id,
        p_provider::public.identity_provider, p_issuer, p_subject
      );

      RETURN QUERY SELECT v_user_id, v_tenant_id;
      RETURN;
    EXCEPTION WHEN unique_violation THEN
      -- O subbloco é revertido; a próxima iteração relê o vínculo vencedor.
    END;
  END LOOP;
END
$$;

ALTER FUNCTION app_private.resolve_or_provision_identity(text, text, text)
  OWNER TO cfi_identity_provisioner;
REVOKE ALL ON FUNCTION app_private.resolve_or_provision_identity(text, text, text)
  FROM PUBLIC;
GRANT EXECUTE ON FUNCTION app_private.resolve_or_provision_identity(text, text, text)
  TO cfi_runtime, cfi_test;

11. Operação e observabilidade

  • Migrations, grants, RLS e seeds administrativos usam papel/URL de migration; runtime nunca recebe essa URL.
  • Seed ou demonstração tenant-owned usa a mesma função de provisionamento e transações contextualizadas, com IDs obviamente fictícios.
  • Logs registram correlation id, operação, resultado e IDs internos quando necessários; não registram token, issuer+subject completos, connection string, nomes ou valores financeiros.
  • Métrica de contexto ausente, policy violation e erro de provisionamento não contém payload.
  • Startup consulta current_user, pg_roles.rolsuper/rolbypassrls e ownership; divergência impede readiness.

13. Defesa em profundidade

Auth0 prova a origem do token; Guard NestJS valida e autoriza; Identity resolve IDs internos; Application carrega TenantContext explícito; repositório inclui filtro de ownership; transaction wrapper fixa o contexto; RLS restringe linhas; constraints preservam integridade. Cada camada cobre uma classe diferente de erro e nenhuma autoriza remover as demais.

14. Riscos residuais

  • Comprometimento de credencial de migration ou da função provisionadora ignora RLS; reduzir acesso, rotacionar e auditar.
  • Foreign keys/unique podem revelar conflito por canal lateral; aplicação não expõe detalhe de recurso alheio.
  • Disponibilidade de criação do papel BYPASSRLS no Neon deve ser comprovada antes da migration real; se indisponível, revisar o ADR.
  • O SQL permanece sujeito a validação executável em PostgreSQL autorizado; esta documentação não afirma execução.

ADR RLSDecisões e fontes

16. Registro de decisões

  • GUC local transacional: evita estado de sessão e acompanha a conexão durante a transação Prisma.
  • Contexto interno explícito: preserva Application/Domain livres de HTTP/Auth0.
  • ENABLE + FORCE nas quatro tabelas: reduz bypass acidental do owner.
  • Runtime não owner e NOBYPASSRLS: requisito operacional bloqueante.
  • Policies separadas: tornam USING/WITH CHECK e cobertura por comando auditáveis.
  • Função provisionadora estreita: resolve o bootstrap sem entregar credencial owner ao tráfego comum.

17. Checklist S1-02/S1-03

  • Criar papéis com segredo fora da migration e validar atributos.
  • Usar conexão direta somente em Prisma Migrate e pooled no runtime.
  • Adicionar helper, grants, 16 policies e FORCE na migration create-only revisada.
  • Implementar resolve/provision com testes de replay e concorrência.
  • Implementar wrapper transacional sem nesting e startup fail-fast.
  • Executar matriz em PostgreSQL isolado e testes Application/Supertest sem dados reais.
